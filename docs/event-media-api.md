# Фотографии мероприятий: контракт API

Базовый адрес: `http://localhost:8080`. Все три маршрута требуют существующий JWT:
`Authorization: Bearer <token>`.
Сначала создайте событие обычным `POST /api/events`, затем используйте полученный `id`.
Создание события остаётся JSON-запросом; фотографии передаются отдельно.

## Права и ограничения

- Загрузка и удаление — только создатель события. Исключения для администратора нет.
- Просмотр активного события и его фото — любой пользователь с JWT, как в существующем API события. Верификация не добавляет ограничения.
- Для неактивного события POST и GET возвращают 404. Владелец может удалить его фото через DELETE, в том числе повторить операцию после сбоя.
- Один POST: ровно один файл в поле `file`, без дополнительных полей. Для нескольких фото — отдельные POST.
- JPEG, PNG, статический WebP. Сервер проверяет содержимое полным декодированием; имени, расширению и MIME клиента не доверяет.
- Максимальный размер файла: **5 242 880 байт (5 МиБ)**.
- Максимальный размер тела HTTP-запроса: **5 308 416 байт**, включая multipart-заголовки. Ограничение применяется и без Content-Length.
- Для ограничения памяти декодирования: не больше **25 000 000 пикселей** на изображение.
- Не больше **5 фото на событие**. Проверка защищена блокировкой строки события в PostgreSQL и работает при параллельных запросах к нескольким экземплярам приложения.
- Bucket остаётся приватным. Ссылки действуют **900 секунд (15 минут)**. Для обновления ссылки повторите GET.
- В БД `file_url` — постоянный ключ `events/{eventID}/{32 hex символа}.{jpg|png|webp}`. В API `file_url` — подписанный временный URL.
- `file_type` — определённый сервером MIME: `image/jpeg`, `image/png`, `image/webp`.
- `order_index` начинается с нуля, новый файл получает индекс после максимального текущего. После удаления возможны пропуски. Сортировка: `order_index`, затем `id`.
- POST и GET возвращают `Cache-Control: no-store`. Подписанная ссылка работает без JWT до истечения срока: не используйте её как постоянную ссылку.
- Адрес S3 берётся из Config и входит в подпись. Для локального браузера это `localhost:9000`; менять хост в подписанном URL нельзя.

## POST /api/events/:id/media

`Content-Type: multipart/form-data; boundary=...`, единственное поле `file`.
Не задавайте Content-Type вручную при использовании FormData или curl: boundary добавляет клиент.

**201 Created** — объект без обёртки:

```json
{
  "id": 42,
  "event_id": 7,
  "file_url": "http://localhost:9000/event-media/events/7/0123456789abcdef0123456789abcdef.jpg?X-Amz-Algorithm=AWS4-HMAC-SHA256&...",
  "file_type": "image/jpeg",
  "order_index": 0,
  "uploaded_at": "2026-11-15T10:00:00Z",
  "created_at": "2026-11-15T10:00:00Z",
  "url_expires_at": "2026-11-15T10:15:00Z"
}
```

`id`, `event_id`, `order_index` — числа. Даты — строки RFC 3339 в UTC, возможны дробные секунды.
URL в примере сокращён; реальный ответ содержит полную подпись.
`uploaded_at` и `created_at` фиксируют начало успешной операции загрузки/создания метаданных.
`url_expires_at` — время истечения ссылки.
После неожиданной сетевой ошибки POST перечитайте список перед повторной загрузкой: POST не имеет ключа идемпотентности.

## GET /api/events/:id/media

**200 OK**. Пустой список:

```json
{"media": []}
```

С фотографиями:

```json
{
  "media": [
    {
      "id": 42,
      "event_id": 7,
      "file_url": "http://localhost:9000/event-media/events/7/0123456789abcdef0123456789abcdef.jpg?X-Amz-Algorithm=AWS4-HMAC-SHA256&...",
      "file_type": "image/jpeg",
      "order_index": 0,
      "uploaded_at": "2026-11-15T10:00:00Z",
      "created_at": "2026-11-15T10:00:00Z",
      "url_expires_at": "2026-11-15T10:15:00Z"
    }
  ]
}
```

Схема элемента совпадает с ответом POST. Существующие ответы маршрутов событий не изменены: галерею загружайте этим отдельным GET.

## DELETE /api/events/:id/media/:mediaId

Тело запроса не требуется. **204 No Content**, без тела ответа.
`mediaId` проверяется вместе с `event_id`: фото другого события возвращает 404 и не удаляется.
После успешного удаления повторный DELETE возвращает **404**, поскольку метаданных уже нет.

При отказе S3 запись БД сохраняется. При успешном удалении из S3 и отказе удаления/фиксации БД метаданные также остаются для повторного DELETE. Повторное удаление уже отсутствующего объекта в S3 безопасно.

## Ошибки

Формат: `{"error":"текст"}`. Внутренние ошибки SDK/SQL и настройки подключения в API не передаются.

- **400** — `invalid id` / `invalid mediaId`: ID не является положительным 32-битным целым.
- **400** — `expected multipart/form-data with one file field`: неверный Content-Type POST.
- **400** — `invalid multipart form`: повреждённое multipart-тело или boundary.
- **400** — `expected exactly one file field and no other fields`: нет файла, неверное имя поля, несколько файлов или дополнительные поля.
- **401** — существующий JWT middleware: `Authorization header is required` / `Invalid token`. Дополнительная проверка ID пользователя: `Unauthorized`.
- **403** — `only the event creator can change photos`.
- **404** — `event not found`: событие отсутствует либо неактивно для POST/GET.
- **404** — `media not found`: фото отсутствует или относится к другому событию.
- **409** — `an event can have at most 5 photos`.
- **413** — `file exceeds 5 MiB` / `request exceeds upload limit`.
- **415** — `file must be a valid JPEG, PNG or WebP image of at most 25 megapixels`.
- **503** — `photo storage is temporarily unavailable`; DELETE можно повторить.
- **500** — `could not complete photo operation`: ошибка БД или другая внутренняя ошибка. После POST перечитайте список, после DELETE повторите удаление, если фото ещё числится.

Порядок проверок: JWT → ID/структура/размер запроса → содержимое файла (POST) → существование/доступ к событию → лимит фото (POST) → S3/БД. При нескольких нарушениях вернётся первая обнаруженная ошибка.

## Компенсация и сбои

После неудачной загрузки или записи метаданных сервер делает до трёх попыток удаления объекта с отдельным таймаутом 12 секунд, даже если HTTP-клиент отключился. Число попыток в SDK также ограничено.
При потере подтверждения COMMIT сервер повторно проверяет метаданные под той же блокировкой события. Объект подтверждённой записи не удаляется; при подтверждённом отсутствии записи запускается компенсация.

Если S3 остаётся недоступным при всех попытках компенсации либо исход COMMIT выяснить нельзя, в журнал выводятся только `event_id` и ключ объекта для последующей сверки/удаления. Новый код не логирует секреты, исходные ошибки SDK или подписанные URL.
Постоянной фоновой очереди очистки нет: после длительной аварии или остановки процесса между PUT и записью БД возможны объекты без метаданных, требующие сверки.
Удаление самих событий работает как раньше и автоматически не очищает S3-фотографии; владелец может удалить их отдельными DELETE.

## Примеры PowerShell / curl.exe

Подставьте действующий JWT, ID события и путь к фото. S3-секрет клиенту не нужен.

```powershell
$token = '<JWT>'
$eventId = 7

# Загрузка; запомните id из ответа.
curl.exe -i -X POST "http://localhost:8080/api/events/$eventId/media" -H "Authorization: Bearer $token" -F "file=@C:/Photos/photo.jpg"

# Список с новыми временными ссылками.
curl.exe -i "http://localhost:8080/api/events/$eventId/media" -H "Authorization: Bearer $token"

# file_url откройте браузером; JWT для подписанной ссылки не нужен.

# Удаление.
$mediaId = 42
curl.exe -i -X DELETE "http://localhost:8080/api/events/$eventId/media/$mediaId" -H "Authorization: Bearer $token"
```

Проверка ограничений: шестое фото — 409; чужой JWT для POST/DELETE — 403; mediaId другого события — 404; текст под именем jpg — 415; файл больше 5 МиБ — 413; запрос без JWT — 401.

## Сборка и проверки

Зависимости требуют **Go 1.26+**; проверено на установленном Go 1.27.1.
Запуск: `go run ./cmd/server`. S3-настройки берутся из существующего Config. Bucket policy менять не требуется.

```powershell
go build ./...
go test ./... -count=1

# Опциональная интеграция с работающими PostgreSQL и Silo.
$env:RUN_MEDIA_INTEGRATION = '1'
go test ./cmd/server -run '^TestEventMediaIntegration$' -count=1 -v
Remove-Item Env:RUN_MEDIA_INTEGRATION
```

Интеграционный тест использует реальный Config и JWT middleware, создаёт собственных временных пользователей, события, метаданные и объекты, затем удаляет их. Существующие данные не редактирует. Обычный go test не подключается к БД/S3.

С реальными PostgreSQL/PostGIS и Silo проверены:

- JWT-маршруты, права владельца и просмотр другим авторизованным пользователем;
- PNG/JPEG/WebP с заведомо неверными именем и Content-Type;
- постоянный ключ в БД, получение исходных байтов по подписанному URL, отказ неподписанному GET приватного объекта;
- чужой mediaId, лимиты файла/запроса, конкурентные загрузки: при одном существующем фото из восьми запросов четыре получают 201 и четыре — 409;
- удаление реального объекта после искусственно вызванного отказа вставки метаданных;
- удаление уже отсутствующего объекта, скрытие неактивного события и очистка его фото владельцем;
- существующие создание события через репозиторий, PostGIS-координаты, верификация через репозиторий, участие и отмена участия через API.

Только тестовыми подменами воспроизведены: длительный отказ S3, отказ удаления метаданных, потеря ответа COMMIT, недоступность БД при выяснении COMMIT, отмена контекста, повторные попытки компенсации. Реальная сетевая авария Silo и остановка процесса посреди операции не моделировались. Модульные HTTP-тесты отдельно проверяют multipart, chunked-запрос сверх лимита, JWT/ID и сокрытие внутренних ошибок.
